# Resume and uncertain outcomes

Keep the original requestId, definition, scope and selected skills SHA. Resume the verified session; tool history and retained mutation intents survive checkpoint. An attempt ID changes on resume but is not a new request or authority.

If an action was submitted or returned unknown, reconcile with fresh cloud_read capacity/fleet/backend, client Deployment, SQL and metrics. There is no operation_status tool. Never resend the same mutation, invent a replacement action ID for it, or roll it back automatically. If desired capacity and membership clearly show its intended effect, continue from that observed state and label the acknowledgement unknown; if ambiguous, resource_wait and reobserve. Explain a persistent mismatch and stop rather than bypassing the trace guard.

Example: first reduction returned unknown, but desired three, fleet three, selected old node absent and retained nodes healthy. Do not retry first reduction. Prepare the second original node's drain under fresh observations, then request a separate 3→2 approval using a new actionId with the SAME requestId. Call request_pause(reason=waiting_approval) immediately; resume after the verified decision. Approval of the first reduction never grants the second.

Missing/stale PgCat waiting/idle/active series, failed probes, unready rollout or booting capacity cannot become zero or healthy. Use resource_wait(seconds=60) for temporary readiness and recheck all relevant facts. Denied approval/control is authoritative: follow supplied block/cancel or human direction; no new scale-in bypass.

After final convergence, both original IDs must be absent, desired two and retained replacements protected/healthy/registered. A gap in traffic collection makes acceptance INCONCLUSIVE even if current error counters are zero. Any failed application operation makes it FAIL. Do not substitute a later clean window for the missing interval or report PASS from a model answer.

If several nodes are unexpectedly unprotected, do not scale in. Use fresh fleet observations to identify every unprotected node. Restore protection only through the scoped protection tool when this is a new, unsubmitted corrective action; observe its effect before proceeding. If the retained trace rejects a repeated mutation, stop and report the conflict rather than inventing identifiers, bypassing the guard or resetting the request.

A provider acknowledgement marked unknown can have its intended capacity/membership effect established by later authoritative observations. Preserve both facts. This alone does not resolve every acceptance question: the separate retained assessment still needs exact approval/gate evidence and the complete application-operation window. Ambiguous application operation outcomes prevent PASS even when cloud capacity converged.
