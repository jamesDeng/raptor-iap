# Dedicated correctness traffic client

This component is a test asset, not a deployed app or evidence of zero-loss replacement. Each replica opens four persistent sessions (three operation emitters and one idle client). Each active session schedules once per second. A logical operation inserts a unique ID and reads it back within a transaction, with a five-second deadline and no SQL retry. A lost commit reply is ambiguous; a PostgreSQL rejection is failure. Failed sessions reconnect for the next distinct operation.

Provide `TEST_DB_DSN_FILE` as a private mounted secret file. Verified TLS is required unless `TEST_EVIDENCE_MODE=local` is explicitly set for disposable local testing. Do not point this asset at platform RDS. Initialize the dedicated database with `testdata/schema.sql` through the reviewed setup path. The application never creates tables at startup or changes schema.

`/ready` needs all four session connections; `/health` measures process health. `/metrics` exposes cumulative process-scoped outcome/scheduling/connection counters and duration sum/count. `/evidence` returns a bounded 8,192-event window plus an atomic counter snapshot. Collect it externally every five seconds from every replica, retaining process identities, boundary samples and all intervening sequence numbers. Missing events, unknown processes, resets and gaps prevent a passing summary. The ring is deliberately bounded; losing older events is observable via `truncated` and sequence gaps.

`cmd/evidence` reads a bounded JSON bundle with `expectedProcesses`, `samples`, and `events` from stdin, emits an explicitly local summary and exits nonzero for fail/inconclusive. This CLI evaluates only the covered sample intervals. It does not certify complete live-window coverage, traffic during missing pods, or provider health. Live acceptance needs an external collector with authoritative pod inventory/start/end windows; this remains an integration dependency. A successful summary of selected samples is not the full replacement acceptance.

SIGTERM stops scheduling, finishes in-flight SQL under its existing deadline and closes sessions. Queued work is counted as skipped. Application restarts must be evaluated across process IDs; counters do not survive restarts. Readiness tracks client connections, not independent PgCat/RDS health, and idle connections can become stale until externally observed.

Run `go test -race ./...` and `go vet ./...`. To include the SQL integration test, set `TEST_LOCAL_POSTGRES_DSN` to a disposable local PostgreSQL database; without it the integration test is explicitly skipped. A container runtime is needed to build the Dockerfile; published image digests must be supplied by the integration owner. Mutable base tags in this build recipe are not a reproducible published release.

`cmd/collect` now records bounded snapshots/events from an operator-supplied fixed JSON roster (`[{"podUid":"...","url":"..."}]`) using `-targets-file`, `-duration` (default five minutes, maximum thirty), and `-interval` (default five seconds). It follows no redirects and accepts no embedded URL credentials/query. Feed its JSON output to `cmd/evidence` for a local summary. HTTP errors, stale snapshots, duplicate/restarted process identities, event gaps or exceeded bounds make the capture inconclusive. It does not implement Kubernetes pod discovery or prove that a fixed roster remained authoritative during rolling pod replacement; central integration must supply lifecycle-aware inventory and preserve evidence across Pod changes. Endpoints are individual replicas, not a load-balanced Service. This closes the local capture gap while retaining the live full-window acceptance dependency.

Evidence reconciliation requires nonempty operation IDs and one covered schedule for each terminal outcome; crossing-boundary or unresolved operations make the selected interval inconclusive rather than canceling out through counter totals. Every expected process must attempt work. The collector's `MaxGap` also bounds scheduling progress gaps (including the first/last boundary); the CLI uses fifteen seconds. This is a bounded local progress check, not proof of one-second cadence. Missing idle connections are retried at most once per scheduling tick with the configured dial deadline and an event for every failure; SQL operations are never retried.
