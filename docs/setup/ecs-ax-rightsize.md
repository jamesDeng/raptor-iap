## Terraform review and bootstrap

The AX stack is `infra-terraform/environments/rdev.ali/ecs-ax` with state prefix `ecs-ax.ali`. The module owns two component-specific RAM policies and attachments. The existing shared GitHub OIDC plan role gains only exact AX state read/lock and policy-read rights. The component owns a dedicated `raptor-ecs-ax-gitops-apply` role because the shared apply role already has the default maximum of ten custom-policy attachments. Its trust is restricted to this repository and the protected `rdev.ali-apply` environment. The dedicated role gains exact AX state write/lock, provider-required read calls (`ecs:Describe*`, `vpc:Describe*`, `sts:GetCallerIdentity`), and `StopInstance`, `StartInstance`, `ModifyInstanceSpec` on the one instance. The read calls use `*` because the provider queries collection endpoints; instance-changing actions remain scoped to the exact ECS ARN. The instance has `prevent_destroy` as well as existing provider deletion protection. The shared OIDC provider and plan role remain prerequisites and are not recreated.

The first targeted Terraform bootstrap created the two component policies, plan attachment and guard, then stopped when the shared apply role reached its ten-policy quota; it did not change the instance. The revised continuation plan must contain only two policy-document updates, the dedicated apply-role create and its policy attachment create. Apply that exact plan with short-lived authorized credentials. Never use the console or CLI to create the role or policies or change the instance type. Rerun the PR workflow after bootstrap and verify its sanitized comment shows only an in-place update of the exact existing instance. A successful comment is required before merge.

The workflow is deliberately manual for live apply. After the approved PR is merged, perform a fresh whole-account bill check against the CNY 1,800 net POC stop line and allow for delayed charges, confirm the AX request queue is idle, confirm the counter CPU request reduction and K3s schedulability, and establish a recoverable stateful-data backup. There was **no** snapshot or automatic snapshot policy for the AX system disk on 2026-11-01. Dispatch `Terraform ECS AX GitOps` from `main` with its exact reviewed source SHA. The workflow encrypts the saved plan, binds it to the source SHA, checks the expected instance ID and exact change shape, and waits at the protected `rdev.ali-apply` environment for owner review before applying the saved plan. The AliCloud provider performs the necessary stop/start for an in-place instance type update; a brief outage and a changed system-assigned public IP are possible.

## Acceptance and rollback

After apply, check the same instance ID, 2 vCPU/16 GiB type, original disk ID/encryption/private IP, K3s node Ready, expected 22 Running Pods and their readiness, volumes and persistent stores, AX server/Redis/bridge/worker health, registration IP versus Pod IP, and a representative guest create, ready, resume and cleanup. Compare startup and guest latency with the pre-change observation. Do not claim a successful size reduction from a Terraform apply alone.

If boot, scheduling or guest acceptance fails, make a new reviewed Terraform plan that changes only the same instance back to `ecs.g7.xlarge`, and apply through the same protected workflow after a fresh cost check. Preserve the counter request reduction until the four-vCPU rollback is healthy. A type rollback cannot restore corrupted disk data; use the pre-change backup if necessary. Measure actual savings only from later posted instance bill rows, separating compute from the unchanged system-disk and traffic charges.
