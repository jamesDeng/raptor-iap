# Minimal Raptor App Questions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking. The user has already selected native execution: implement in this session with executing-plans, then conduct one fresh whole-branch review.

**Goal:** Let the owner register an app, ask a natural-language question in a local Raptor UI, and receive a real Pi sandbox answer grounded in that app's saved context.

**Architecture:** A loopback Raptor service and separate gateway worker share a protected SQLite task store. The worker reuses the canonical sandbox lifecycle, with durable task binding and private answer artifacts. Pi has one custom context tool; it reads the immutable snapshot and calls OpenAI directly using the retained OAuth session.

**Tech Stack:** Python 3.12 standard library (`sqlite3`, `http.server`, `fcntl`, `unittest`); HTML/CSS/JavaScript without a build framework; Node 22.23.3; Pi 0.99.2; existing pinned lifecycle SDK dependencies. No new web package, queue service or cloud hosting.

**Spec:** [Approved architectural design](../specs/2026-10-04-raptor-app-questions.md).

## Global Constraints

- Local, single-owner UI/API; separate local worker; one active Pi run for the shared renewable account. Preserve the user's native execution choice.
- Singapore `ap-southeast-1`; Pi `0.99.2`; Node `22.23.3`; GPT-5.6 Luna (`gpt-5.6-luna`) through retained ChatGPT Pro OAuth. No silent model fallback or model proxy.
- Sandbox lifetime 900 seconds; model timeout 90 seconds; maximum three assistant turns; 1,024 output tokens per response; no automatic model or whole-request retry.
- Question at most 2,000 characters and 8 KiB UTF-8; snapshot at most 32 KiB and ten dependencies; answer at most 16 KiB UTF-8. Reject unknown fields and booleans where integers are required.
- Every task saves a single app's immutable owner-entered snapshot/version. `present` is an owner declaration; blank resource identifiers mean unknown. No live discovery claim.
- Dependencies use type `postgres`, `pgcat`, `other` and lifecycle `planned`, `present`, `unknown`. Do not store credentials, connection strings or kubeconfig as app context.
- Enable only `get_application_context` for app questions. Disable built-in tools, extensions, skills, automatic context discovery, retry and compaction. Preserve the generated `read-probe` path.
- No question, snapshot, answer, credentials or raw provider errors in canonical ledger/status output, public repository, CI output or acceptance receipts. Private task storage uses directories 0700 and files 0600.
- Require context-tool execution and a nonempty settled answer for answer success. Preserve distinct answer, checkpoint and cleanup outcomes; success is not proof of semantic correctness.
- Never automatically replay a claimed task after interruption. Uncertain mapping, persistence, creation or cleanup blocks dispatch; known resources remain recoverable.
- Queued cancellation only; explicit retry creates a new attempt/history. Active cancellation, Pi conversation resumption, interactive approval/clarification pauses and token streaming are deferred.
- Reuse existing encrypted OSS checkpoint/storage and locks; retain original credential storage and Terraform state. The refresh-before-checkpoint crash limitation remains accepted.
- Total Aliyun POC spend below RMB1,000; budget preflight before paid tests. No new always-on compute or account-wide spending-cap claim.
- App restart, GitOps PRs, ACK/Argo CD installation, RDS/PgCat deployment and replacement tests are later slices.

## Review Focus

1. Browser retries or double-clicks must create one task, while a genuinely new request creates another: idempotency and conflicting-key tests in Task 1/5.
2. Worker death between SQLite claim and ledger publication must never replay the question: crash-window and foreign-binding tests in Task 4.
3. A valid answer followed by failed checkpoint, local result write or cleanup must retain truthful independent outcomes and block unsafe dispatch: Task 3/4.
4. Cross-origin requests, host rebinding, injected HTML, multibyte inputs and another task's result must be rejected or rendered as text: Task 1/3/5/6.
5. Prompt instructions to read credentials, run commands or substitute another app must find no corresponding tool or selectable context: real SDK and binding tests in Task 2/3.

Use a canonical ignored `.raptor-local/raptor/` beside the primary checkout's Git common directory for SQLite, request token and worker lock. Use the existing canonical `.raptor-local/sandbox-lifecycle/<account>/` for ledger and task-result artifacts. All worktrees resolve the same directories. Neither service accepts an alternate database/ledger location from a web request. Tests inject isolated resolved temporary directories through constructors only.

SQLite tables: `apps`, `tasks`, `attempts`, `events`, singleton `dispatch_gate`, `recovery_requests`. Enable foreign keys, WAL, `synchronous=FULL`, busy timeout 5 seconds; use `BEGIN IMMEDIATE` for transitions. UUIDs are server-generated canonical UUID strings. An attempt ID is also its lifecycle `attempt_id`; queue order is a database monotonic sequence. Do not use time-based leases or SQLite row deletion to establish ownership.

Types in `models.py`: validated `AppRecord`, `AppSnapshot`, `TaskRecord`, `AttemptRecord`, `TaskBinding(task_id, attempt_id, snapshot_sha256)` and `OutcomeReport(answer, checkpoint, cleanup, overall, error)`. Binding hashes canonical compact recursively sorted-key UTF-8 JSON (`ensure_ascii=False`), identically in Python and Node. Character limits count Unicode code points, including emoji, rather than JavaScript UTF-16 code units. Outcome enums: answer `completed|failed|unknown`; checkpoint `saved|failed|unknown`; cleanup `confirmed|failed|unknown`; overall `completed|failed|blocked`. A recovery that confirms cleanup cannot change unknown inference to completed without bound result evidence.

App creation/edit input: `name`, `owner`, `environment`, `region`, nullable `ack_cluster_id`, `namespace`, `deployment`, `dependencies`; generated ID/version/UTC timestamps/provenance are not editable. Trim metadata fields, allow question whitespace internally, reject blank questions. Name/owner/environment/region/identifiers max 128 characters each; dependency notes max 1,000 characters. Snapshot contains the saved record plus `provenance="owner-entered"`; it must satisfy both field bounds and the total byte cap. Reject obvious credential/connection-string input with a fixed validation message; this is not a general secret-detection guarantee.

Task creation input: `app_id`, `question`, `model`, `idempotency_key` (browser-generated UUID). Canonical request hash covers these fields excluding the key. Same key/hash returns the existing task; same key/different hash returns conflict. Task snapshot/question/model never mutate. Retry uses the original task snapshot/model and creates one new attempt only after the previous attempt is terminal and recovery has confirmed the account safe. Retries and recovery actions also accept an idempotency UUID. App edits require expected version; stale edits return conflict.

Progress event enum: `queued`, `starting`, `restoring-credentials`, `asking-agent`, `saving-checkpoint`, `cleaning-up`, `finished`. Attempts have state `queued|claimed|completed|failed|blocked|cancelled`; store latest stage independently from outcomes. An interrupted claimed attempt is blocked until explicit recovery, even if the next question would be harmless.

### Task 4: Dispatch and recover without replaying a question

**Files:** `tools/task_store/gateway.py`, `components/agent-gateway/worker.py`, lifecycle locked helpers, store transitions; `tests/test_raptor_gateway.py`, existing lifecycle tests.

**Interfaces:** `Gateway(store: Store, cfg: Config, cloud: Cloud, ledger_path: Path)`; `tick() -> bool` processes at most one recovery or task; `reconcile() -> None` identifies interrupted ownership without starting inference. `worker_lock(root: Path) -> ContextManager` holds nonblocking flock for the process lifetime. Split existing lifecycle into `_execute_locked(cfg, request, path, cloud, *, binding=None, observer=None) -> dict` and current locking `execute(...)` wrapper; `_recover_locked` remains the locked recovery boundary. `observer(stage: str) -> None` receives allowlisted progress only. All entry points use the same canonical account lock.

Lock/order algorithm: process worker lock → canonical lifecycle account lock → reconcile/check gate → short SQLite claim transaction → persist identical task/attempt/snapshot binding in ledger before any external creation → execute under that already-held lock. No SQLite transaction spans cloud calls. Account `Busy` leaves tasks queued/unclaimed. Preserve binding when phases reset; the allocated task attempt UUID becomes lifecycle attempt UUID. Direct CLI is excluded by the account lock and cannot accidentally clear the task-store gate.

Recovery algorithm: on startup, any claimed/nonterminal attempt becomes blocked, without inference. Reconcile exact ledger task binding and attempt ID; conflicting/unmapped app bindings block globally. Only an explicit queued recovery control action invokes `_recover_locked` under the same locks. Inspect the known private artifact and completed runner result, clean known resources, then finalize with observed independent outcomes. A claim with no matching ledger can be closed as unknown only after confirming no pending/known resources and no conflicting binding; do not assume the question completed. Failed recovery retains the gate. Clear a matching gate only after confirmed account safety and successful durable ledger/store writes, never while persistence is uncertain; failed/unknown task stays terminal until explicit retry. Recovery does not submit inference. An interrupted recovery control action is re-reconciled under the same idempotency key; it may repeat cleanup checks, never inference.
