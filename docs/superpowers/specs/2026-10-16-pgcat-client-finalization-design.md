# PgCat live-test client finalization amendment

Status: design for review. This amends the approved [two-node live-test design](2026-10-16-pgcat-two-node-live-test-design.md) only at its traffic-window close. It does not authorize a live replacement, credential transfer, Gateway flag change, or a client finish operation.

## Purpose and boundary

The full two-node 2→4→3→2 run needs one retained traffic window across both approval pauses and an explicit final marker from every client process seen in that window. The current two client Pods run indefinitely. SIGTERM emits a final marker but the Pod exits ten seconds later; Argo self-heals the two-replica Deployment, and a replacement process can appear before the collector closes. An imperative scale-down races Argo. Consequently the current runbook blocks full-run traffic PASS. This amendment provides a controlled end to scheduling without changing the Deployment's desired replica count.

The target remains only the `rdev.ali` traffic client for `A00003` / `DP00001` / `D00002`. The worker collector remains on the verified ACK worker and uses the existing temporary private kubeconfig only after separate, specific authorization. No new cloud resource, IAM role, network endpoint, or secret is part of this amendment. `replacementEnabled` remains false throughout disabled-mode verification.

## Client control and identity

Each client Pod mounts a writable memory-backed `emptyDir` at `/run/traffic-control`; the regular non-root client process creates a mode-0600 Unix socket there. There is no TCP finish endpoint. The existing distroless image uses its `/client` binary for both normal service mode and a `finish` subcommand, so `kubectl exec` needs no shell. The chart exposes its own immutable Pod UID through the downward API. The client retains its random process ID from the evidence store.

The command takes an expected Pod UID and expected process ID. The server compares both to its own values before changing state and returns only a sanitized status. A mismatch refuses the finish. A second command for the same identity reports the already-started or final state without starting a second drain. If the exec acknowledgement is unknown, the operator reads exact `/evidence` and Pod identity; it does not blindly send another finish command. Socket absence, wrong mode, or malformed request fails closed.

The finish transition stops the tick source so the Runner stops scheduling new SQL work without cancelling its context. Closing its job queues lets already scheduled work run to its existing finite deadline. The Runner then closes every session, and the store sets `final=true` only after `Scheduled = Attempts + Skipped` and `Connected = 0`. A finish during ordinary traffic must not create a new `Skipped` event. The final snapshot and `traffic_final` log record keep the same allowlisted fields as the existing client. The evidence and metrics HTTP server stays up while the process holds final evidence. `/ready` becomes false after sessions close; `/health` remains true during the hold. A normal SIGTERM still follows the existing bounded shutdown path and does not claim a successful controlled finish if work was skipped or final evidence was lost.

The hold ends after two minutes, then the process exits. The existing GitOps-owned Deployment still desires two replicas; Kubernetes replaces the exited Pods. The operator verifies two *new* Ready processes and healthy SQL/metrics before calling restoration complete. A Pod exit, restart, or deletion before its final snapshot is durably captured makes traffic assessment INCONCLUSIVE. Restored processes are outside the closed measured window and cannot substitute for missing finals. The chart keeps two replicas, its existing service account setting and probes, and Argo self-heal.

## Worker boundary and evidence

The worker records an exact roster of the two current Pod names, UIDs, and process IDs after fleet convergence and before finalization. It refuses a changed or incomplete roster. One operator action marks a local capture boundary and sends one `kubectl exec <exact-pod> -- /client finish --expected-pod-uid ... --expected-process-id ...` call to each Pod concurrently. The worker never prints or retains kubeconfig, DSN, or Secret values. The finish action is a runtime operation requiring separate action-time authorization; it is not a provisioner.

The collector keeps one process, clock, sequence state, and ordered manifest across all segment rotations. Measurement frames continue until the explicit boundary; settling frames begin there, including a frame in which only one client has finalized. Its current five-second settling limit remains unchanged. It reads final snapshots for both bound identities, retains them in fsynced allowlisted JSONL, and closes the capture only when every observed process has a final marker and the bound clients have settled. It then writes and hashes the completion manifest and assesses the complete stream. The prior final snapshots from any mid-run client restarts remain required. A timeout, command error, UID/process mismatch, missed poll, missing final, or settling beyond five seconds yields INCONCLUSIVE; any observed SQL failure, timeout, or ambiguous operation yields FAIL regardless of those gaps. Neither a successful command acknowledgement nor a later clean window can yield PASS on its own.

The two-minute hold is a retention ceiling, not a relaxation of the five-second assessment limit. A slow operation or delayed poll may make the run INCONCLUSIVE; the worker must not extend the bound after observing that outcome. If finalization fails, preserve the observed fleet and evidence, stop new replacement mutations, allow bounded client restoration, and reconcile exact current state. The Gateway flag is restored to false only after the active attempt settles and the existing guarded rollout can be verified.

## Verification and rollout

Use test-driven changes in the existing client, worker collector, and Helm/GitOps materials. Go tests cover UID/process matching, socket permissions, duplicate or uncertain commands, graceful queue drain without new skipped work, bounded hold, SIGTERM, final evidence and readiness/liveness. Python fixtures cover exact-roster parallel dispatch, measurement-to-settling boundary, both finals within five seconds, process restart history, missed/late final, and FAIL precedence over INCONCLUSIVE. Helm/GitOps checks verify the Pod UID field, private memory volume, distroless command, unchanged desired two replicas, and no new RBAC or network exposure.

Review the code and use the existing PR, immutable image digest, and Argo GitOps flow. Confirm the live image digest, exact Pod specs, two Ready clients, and `replacementEnabled=false`. With replacement disabled, run a short worker capture and controlled finish as a path proof, verify final markers and capture manifest, then verify automatic restoration to two Ready new clients with healthy SQL/metrics. This path proof does not prove replacement traffic acceptance. A full live run still requires fresh provider/cost/time/credential preflight, the two exact human scale-in approvals, and separate action-time authorization for the worker kubeconfig transfer, guarded flag enablement, replacement, and final client finish. If any qualification is missing, stop at the specific blocker rather than claim PASS.
