## Existing state and approaches

The Terraform PR plan/comment and reviewed main apply gates already exist and were exercised. The Gateway Helm release references `gateway-live-config` but does not provision its values. The live Secret's nonsecret metadata showed `kubectl-create` on 2026-10-07 and `kubectl-replace` on 2026-10-13. No SSO or OSS reconciliation process for this Gateway Secret was found. Private JSON snapshots under `working/replacement-deployment-2026-10-11/` are older than the live Secret, contain sensitive material, and are not update inputs. The project uses encrypted OSS for other credentials and checkpoints; that does not establish an OSS source of truth for this Secret.

Chosen approach: a narrow operator tool reads the current live Secret in memory, validates its exact namespace/name, structure, scope, current flag, and `resourceVersion`, changes only `replacementEnabled`, and replaces it with optimistic concurrency. It prints only sanitized status and never writes Secret payloads to Git, logs, shell arguments, receipts, or temporary files. Any concurrent update, unexpected field, scope mismatch, or non-idle Gateway blocks the operation. After a guarded, observed Gateway rollout it reads back only the flag and deployment readiness. The same guard restores `false` after the attempt settles. This is an approved runtime configuration operation, separate from Terraform cloud provisioning. Manual editing of an old snapshot and a new OSS sync subsystem are outside this POC.

The ACK console Workbench shell has valid Kubernetes read access but no Python and no direct client Pod-IP access. The local Workbench CLI reaches the exact ACK worker `i-t4nj1bitmcz7cuoch82h`, but its default `kubectl` has no active kubeconfig. The chosen collector location is that worker, matching the existing collector contract. A short-lived private-network kubeconfig may be transferred to only this worker through the documented Workbench path after separate, specific authorization. The local and remote copies must be mode 0600 and removed after the run, including failure. Denial of that transfer blocks the live test; do not substitute another transport or expose the ACK API.

## Preparation and data flow

1. Correct the retained collector's obsolete UUID Prometheus selectors to exact `rdev.ali` / `DP00001` / `D00002` labels, scope the `up` series as well as pool series, and test missing, duplicate, stale, foreign, and nonintegral observations. The deployed metrics values already use catalog codes. Pin source and worker artifact hashes for the run.
2. Replace the stale one-shot provider-inventory helper with a bounded operator process using the existing Alibaba profile. It reads authoritative ESS, ECS, and NLB state for the exact target at least every 15 seconds, records `observedAt`, desired capacity, complete member IDs, and healthy registered IDs, and atomically publishes nonsecret inventory to the worker through Workbench. On membership change it refreshes only the existing `pgcat-provider-inventory` metrics target ConfigMap from verified private ECS addresses. It never guesses targets or treats an old ConfigMap as live provider evidence. A publication failure or inventory age over 30 seconds is visible to the assessor and cannot produce PASS.
3. The worker collector discovers the two traffic client Pod UIDs and reads each process's `/evidence` endpoint and the private Prometheus service every second. It fsyncs allowlisted JSONL outside Pods. It records raw source timestamps, all pool/user active/idle/waiting triplets, the current provider roster, and explicit client final markers. No DSN, SQL payload, token, or Secret value is retained.
4. A single collector process rotates output into individually bounded segments of at most 30 minutes while preserving one ordered assessment stream across segment boundaries. The whole capture is bounded to 90 minutes. Rotation cannot create a poll gap or reset Pod/process identity, event sequence, or counters. A separate completion manifest binds segment hashes, start/end, missing-poll count, and the explicit final marker. Missing or ambiguous segments make the whole window INCONCLUSIVE; a later clean segment cannot replace a missing interval.
5. Before enablement, perform a short live capture with replacement still disabled. Confirm direct client and metrics reachability from the worker, exact provider roster, fresh complete series for `test` / `poc_app`, one-second poll continuity, and an explicit completion marker. This proves the capture path, not replacement acceptance.

The existing chart owns the client and metrics deployments. Dynamic provider inventory is operational evidence and target reconciliation, not a new cloud provisioning path. Any required IAM expansion, new controller, or new cloud resource discovered during implementation returns to a reviewed Terraform PR with sanitized plan comment and reviewed apply before use.

## Replacement execution and gates

Start only after verifying current cost and a forecast within the owner-amended CNY 1,200 net pretax whole-POC ceiling for this run (originally RMB 1,000), an idle Gateway, signed-in operator access, healthy 2/2 client and 1/1 metrics workloads, exactly two protected healthy ESS originals, desired two/max four, both NLB backends healthy, fresh PgCat metrics, and read-only SQL probes. Do not start after 21:30 Asia/Shanghai because the owner's daily resource stop is at 23:59. Stop new mutations by 22:45 and reserve time for reconciliation and credential cleanup. If the time budget cannot cover the whole run, defer it.

After the collector is running and preflight is fresh, enable the Gateway flag through the guarded Secret workflow and verify the rollout. Create one new immutable Raptor `db-proxy.replace-nodes` request in `replacement` mode, model `gpt-6-luna`, pinned `skills-v0.4.0`, exact resolved scope. Keep the request ID, definition SHA, selected skill SHA, and scope fixed across resumes.

The agent records the two originals, protects them, expands once from two to four, qualifies both new nodes by healthy NLB registration and SQL probes, and protects the new nodes. It then deregisters and drains only one original, restarts only the bound client Deployment, and requires complete zero active/idle/waiting PgCat client counts for that original across all reported pools/users. A distinct exact human approval for 4→3 is required. The agent pauses, resumes only after the verified decision, gathers fresh evidence, and submits the approved scale action once. It repeats the same sequence for the other original with a different action ID and a separate exact 3→2 approval. Conversation text and prior approval do not grant scale-in authority. The owner accepts connections that arrive between zero-client observation and termination; this design does not promise zero failures.

Submitted or unknown mutation acknowledgements are not convergence. Reconcile desired capacity, ESS membership, NLB membership, deployment, SQL, and metrics from fresh authoritative reads. Never resend an acknowledged or unknown action or invent a replacement action ID. If state remains ambiguous, stop further scale-in and report the observed fleet. Do not automatically reverse a scale action. Preserve protection on retained healthy nodes; any corrective protection is separately scoped and verified. A denied approval or stale/missing gate is final for that action.

## Acceptance, cleanup, and recovery

Operational convergence requires desired two, both originals absent, two distinct new nodes protected/healthy/registered, successful SQL probes, and bound client readiness. The Gateway's convergence answer remains `acceptance: pending` until a separate assessment joins the complete retained traffic window with exact approval and control evidence. PASS requires covered successful traffic, continuous active roster and scheduling, complete fresh provider/metrics coverage, no failed, timed-out, ambiguous, or skipped SQL operations, no poll gap over three seconds, settled boundary work, and explicit completion. A failed operation yields FAIL; missing coverage or uncertain lifecycle yields INCONCLUSIVE. Never call either outcome PASS from a model answer, point-in-time zero counter, or a later clean window.

On any unresolved fault, stop new mutations and preserve the observed fleet and evidence. Restore `replacementEnabled=false` after the active attempt has settled and the Gateway can be rolled safely; verify the running Gateway state. Confirm request checkpoint status, sandbox/key absence, access revocation, and final fleet/client state. Remove the temporary local and worker kubeconfig and run files after privately retaining the allowlisted evidence, completion manifest, checksums, and sanitized receipt in the existing encrypted OSS evidence prefix with its bounded lifecycle. Retain no credentials in the evidence bundle. If a partial fleet remains, report exact capacity, membership, protection, backend, and traffic state for a separate reviewed recovery action.

## Verification before live execution

Use fixture tests for Secret exact-field update, optimistic concurrency, wrong target/scope, stale snapshot, no secret output, and flag restoration; collector label selectors, provider changes, timestamp limits, segment overlap/continuity, Pod restarts/final markers, all failure and inconclusive conditions; and request-bound 2→4→3→2 approvals and uncertain-action reconciliation. Run affected Go, Python, Node, Helm, and GitOps checks. Review the change and deploy through the existing PR/image pin/Argo flow. Verify the live images and selected skills SHA, then perform the disabled-mode capture. Before any credential transfer or actual replacement, present the exact artifact, target, duration, cleanup command, and latest cost and preflight observations for action-time authorization.
