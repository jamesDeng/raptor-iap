# PgCat rehearsal continuity after the first live 2→3→2 attempt

## Intent and observed failure

The 2026-10-26 replacement-disabled rehearsal returned the Singapore PgCat fleet to its two protected originals, but its continuous capture is **INCONCLUSIVE**. The private archive `traffic-evidence/pgcat-scaleout-20261026-1627/rehearsal-inconclusive-evidence.tgz` is the evidence, not a passing fixture. It has 1,189 frames and 7,134 successful SQL operations, with no observed failure/timeout/ambiguity/skips, but the strict assessor found metric, roster, poll and provider freshness gaps. No full replacement request followed it.

The startup hypothesis was supported: the new Pending:Wait node gained complete raw metrics at `08:56:30Z`, before first NLB registration at `09:01:57Z`; every backend frame before recovery had complete metrics. The later failures occurred in the rehearsal's operator-controlled return to two:

- The required client Deployment restart produced one `expectedReplicas=0` frame, temporary three-Pod frames, and a 3.614-second poll gap. A frame stamped before the rollout call completed received future-dated metrics, triggering stale-metric/raw reasons. The old and new processes eventually had final markers, but that does not repair the in-window gaps.
- After a zero-connection observation and a later fresh provider publication showing the new node absent from NLB, the exporter disappeared while ESS still reported the drained node `InService`/`Removing`. The assessor's unconditional nonpending-member requirement kept demanding metrics for this **NLB-absent, zero-client** node for 24 frames. It correctly continues to demand complete metrics for every actual NLB backend.
- The provider feed's last successful publication was sequence 76. The local Workbench daemon recorded inventory execution deadlines/timeouts near the final target readback. The feed stopped at `inventory-write`; the precise transport-level stall is not exposed by the sanitized feed error. Extra Workbench status calls while that feed was active are a plausible contributor, not a proven sole cause.

## Approaches

1. Repeat the same restart and Workbench polling. This repeats observed invalid frames and paid scale actions; reject.
2. **Selected:** for the disabled rehearsal, use the running clients' observed zero-connection drain instead of a Deployment restart when safe; align the assessor's old-node retirement with the already approved zero-plus-later-backend-absence rule; publish a private local feed success receipt so the operator can stop the feed before final client finish without another Workbench status call. This changes neither PgCat nor the Gateway/AX images and preserves strict gaps as INCONCLUSIVE.
3. Add an in-cluster provider controller and traffic orchestrator. This could remove Workbench contention but adds a new workload, cloud credential path and review surface; defer unless the bounded local fix still fails.

## Runtime contract

- The Gateway stays `replacementEnabled=false` throughout another rehearsal. Keep one continuous schema-2 `disabled-rehearsal` feed session and collector. No archived window is relabeled; no evidence is spliced or retried under an uncertain action ID.
- After the new node is removed from NLB, keep the exact same two client process identities running if both have advancing successful SQL and zero Failure/Timeout/Ambiguous/Skipped. Require two distinct fresh complete zero active/idle/waiting samples for **every** pool/user on the drained node and a later fresh provider publication showing backend absence. If any connection remains, a client/process changes, or a traffic/metric gate fails, stop assessment, then perform separately reviewed recovery outside the assessed window. Never restart clients to manufacture a PASS.
- The assessor may retire a previously registered node's metric obligation only after its complete fresh zero observation and a later fresh provider publication showing it absent from NLB. That retirement applies even while ESS still lists the drained node. Any current NLB backend, including Adding/Removing/Unhealthy, always requires fresh `up=1` and complete raw triplets. A reappearing backend or a later nonzero sample restores the obligation. Missing zero, stale/incomplete zero, same provider publication, or backend still present remains INCONCLUSIVE. Poll, source-age, SQL and client-roster limits remain unchanged.
- The local provider feed optionally writes a mode-0600, address-free status receipt **only after** successful worker publication. It contains the session, sequence, mode, desired count and observation time. A failed/uncertain worker write never advances it. The receipt is operational liveness, not retained acceptance evidence and not a substitute for an exact ConfigMap readback or later collector frame.
- At final two-node reconciliation, patch only the existing target ConfigMap with its live resourceVersion and read it back. Observe a later local success receipt for the same session and a corresponding clean collector frame; then stop the feed intentionally and invoke one exact `finish_clients.py` boundary while the last provider observation is still under 30 seconds old. No Workbench status polling while the feed is active after final reconciliation. Failure to close inside the freshness limit is INCONCLUSIVE, not a reason to restart a feed or widen the limit.

A worker write failure or changed session cannot produce a success receipt. Keep the existing 15-second absolute refresh deadline and no Workbench write retry.
- Test the revised no-restart recovery gate with a short synthetic window; assert changed client identity, nonzero/stale samples, or incomplete target readback cannot pass. Update the active runbook; prior attempted evidence stays INCONCLUSIVE.

A new paid 2→3→2 rehearsal starts only if that check, current one-operator/cost/time gates and exact fleet baseline pass. A full 2→4→3→2 request starts only after the **new** rehearsal independently assesses PASS and cleanup is verified.
