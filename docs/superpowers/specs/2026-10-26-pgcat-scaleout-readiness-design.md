# PgCat Scale-Out Readiness Before NLB Registration

## Intent and evidence

The full request `570533ed-e417-4bc5-beba-ad4db3db8d20` reached desired capacity four but ended `ToolFailed` before approval or scale-in. The retained continuous capture is INCONCLUSIVE: the two new NLB backends appeared while unhealthy and without complete fresh PgCat metrics. The resumed agent then made read calls before this readiness was established; `metrics_read` returned HTTP 503 and `deployment_read` failed concurrently. The exact underlying cause of the deployment read failure is still unknown and must not be inferred from the metrics failure. Recovery to the two protected originals is complete; observed recovery SQL timeouts/skips remain recorded.

The current Terraform scaling configuration installs Docker, pulls the PgCat image, then starts the container in ECS user data. The ESS server-group attachment automatically registers a new node in NLB independently of that startup. The provider feed can publish a Pending node's private metrics target before registration, but the current deployment has no scale-out gate. The pinned skill says to wait for readiness; the runtime allows a metric read while the node is still starting, which converts an expected transition into a terminal tool error.

## Goals and constraints

- Keep the strict continuous-window rule: every NLB backend, including Adding or Unhealthy, needs fresh successful scrape and complete raw active/idle/waiting triplets. Do not reinterpret the failed run as PASS.
- Keep GPT-6 Luna, immutable skills-v0.4.0, exact request scope, human scale-in approvals, Terraform/GitOps resource ownership, no credential exposure and `replacementEnabled=false` until a separately gated run.
- Do not charge for another full attempt until a disabled-mode proof demonstrates that a Pending node can gain metrics coverage before NLB registration and the agent can wait without a tool failure.
- A timeout or uncertain lifecycle completion must fail closed and enter reviewed recovery; never submit an unknown action twice. Retain full traffic, provider, approval and cleanup evidence.

## Approaches considered

1. **Deferred stronger gate: Terraform-owned scale-out lifecycle hook plus a one-use readiness controller.** An ESS `SCALE_OUT` hook would hold new instances in `Pending:Wait` before NLB registration. A local controller would bind the exact activity and two new IDs, verify PgCat and fresh metrics, then complete the lifecycle action; a timeout would roll back. This needs a new private SQL probe and a proven binding from the accepted scale action to the provider activity/token. Neither exists today, so it is not selected for this POC iteration.
2. **Selected for this cost-limited POC: a Terraform-owned 420-second scale-out hook with automatic `CONTINUE`, transition-aware observations and a one-node rehearsal.** This holds registration while the ordinary bootstrap and Prometheus scrape start, without adding an operator that consumes lifecycle tokens. It cannot guarantee readiness if bootstrap exceeds 420 seconds; the strict collector will report INCONCLUSIVE and the operator must recover instead of claiming PASS. The disabled-mode one-node rehearsal measures whether this margin is real before a full attempt.
3. A grace period in the collector or excluding unhealthy NLB backends would reduce code, but weakens the approved full-window evidence rule and could hide failed traffic. It is rejected.

## Runtime contract

Terraform adds exactly one component-owned ESS `SCALE_OUT` lifecycle hook to the existing PgCat module with `heartbeat_timeout=420` seconds and `default_result=CONTINUE`. The Terraform plan/comment and reviewed apply flow must show only the intended hook. Existing ESS/NLB addresses, attachments, IAM and desired capacity stay owned by their current state; no manual creation or replacement is allowed. Record the actual provider hook ID/configuration after apply. This is a startup hold, not a proof: a bootstrap slower than the hold is an explicit failed rehearsal/full-run risk, bounded by the existing evidence and recovery gates.

Before the full run, a disabled-mode 2→3→2 rehearsal starts the continuous provider feed with `--mode disabled-rehearsal` and keeps the Gateway flag false. The optional schema-2 `mode` is retained through capture segmentation and private archive reassessment; absence keeps historical `full-replacement` behavior. Rehearsal mode binds the initial exact two IDs, permits exactly one new ID at desired three, then only that new ID’s departure after desired two. Mode/session changes, changed IDs, original departures and skipped or repeated transitions fail closed. Final assessment requires return to the same two healthy originals; a no-scale capture cannot qualify as a rehearsal. Keep the same feed/capture through final two-target reconciliation, readback and a subsequent fresh two-node metric frame. The operator records one exact group/hook/original-node scope, starts one non-retried desired-capacity-three runtime action and observes the Pending node and NLB registration. No lifecycle token is acquired or completed by the operator. The rehearsal has an absolute deadline and uses the approved staged drain/restart/zero-client recovery to return to the two protected originals. An unknown scale acknowledgement stops; it is never replayed. This limited rehearsal is additional to, not a substitute for, the full two-node 2→4→3→2 request.

The existing provider feed may publish a Pending node's private metrics target as soon as ECS assigns an address. During the 420-second hold, record whether that node becomes `up=1` with complete fresh raw active/idle/waiting triplets before NLB registration. Once registration occurs, require fresh healthy NLB and the same complete metrics on every backend; any gap in the retained window is INCONCLUSIVE. A missed scrape or unhealthy new backend at the hold boundary stops the rehearsal/full attempt and enters reviewed recovery. The full agent may advance beyond scale-out only after fresh four-node healthy NLB, complete metrics and successful SQL probes.

While a new node is Pending and absent from NLB, `metrics_read pgcatClients` must not turn its expected missing metrics into `ToolFailed`. It should report exact pending IDs and validated metrics for the two current backends, in a shape that cannot satisfy any approval or completion gate. If a Pending node appears in NLB, it immediately requires the same full metric coverage as every other backend. `cloud_read backend` must represent documented `Adding`, `Configuring` and `Removing` states as unhealthy transition data rather than an invalid API response; unknown state or mismatched identity still fails. `db_connection_probe` on a known Pending/unhealthy node returns explicit not-ready without attempting credential use, while a healthy registered node still requires a successful read-only SQL probe. All scope mismatches, expired sources and malformed values still fail. The agent system instructions require cloud fleet/backend/capacity checks and `resource_wait` on pending readiness before SQL/new-node mutation; selected skills-v0.4.0 remains unchanged. Metric reads retain the oldest and newest Prometheus response and scrape timestamps, recheck the existing 15-second scrape and 30-second response limits at collection completion, and carry those ages into the 30-second witness freshness/alignment check. A verified reopened witness checks ages at its recorded creation time, preserving a valid historical milestone across later waits. Only the two exact new IDs derived from the baseline and current fleet contribute SQL probes; benign original-node probes do not block them. A runtime gate withholds post-expansion writes and approval requests until fresh four-node backend, metric and SQL evidence is complete; an attempted early write never reaches Infra.

## Verification and rollout

- Test Terraform module and PR plan/comment, then reviewed apply/readback. Test the exact 420-second `SCALE_OUT`/`CONTINUE` hook, Pending target publication, transition states, an unexpectedly registered Pending backend, post-expansion write lock, and missing/expired metrics with fixtures before running on Alibaba.
- Test the observation and model boundary with Pending nodes, incomplete but allowed pre-registration scrapes, and complete metrics before and after registration. A registered backend with any missing series remains a hard failure. Existing baseline, approval, resource-wait, trace and completion tests remain green.
- First perform a disabled-mode rollout and short capture with the hook configured but no scale-out. Then run one bounded disabled-mode **2→3** readiness rehearsal under the remaining cost/time gate; require the exact node to be scraped before backend registration, a complete strict capture, and staged 3→2 recovery of that exact node. Keep the Gateway flag false throughout. Only after the rehearsal, full target reconciliation and cleanup pass may a new full request start with the usual flag, approvals and continuous capture.
- A failed readiness rehearsal is INCONCLUSIVE or FAIL according to actual evidence, never an excuse to relax the assessor. Restore the original two-node fleet, exact targets, false Gateway flag and temporary credential cleanup before another attempt.
